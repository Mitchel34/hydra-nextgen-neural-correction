# Checkpoint publication contract

The owner has authorized regular future commits and pushes to this curated public neural-correction repository as research advances. This contract is checkpoint-driven and creates no schedule, service, spending authority or permission to expose a private research repository.

1. Start from a durable research checkpoint. Record the source version and exact file hashes privately, together with the evidence supporting each proposed public claim. Distinguish generation tooling, outlet experiments and the current internal-correction continuation. Never infer scientific success from a task title, passing synthetic test, elapsed time or a proposal.
2. Prepare an isolated checkout of this public repository. Keep active research trees, processes, evidence and the shared resource registry untouched. Curate an explicit file allowlist. Do not copy the private repository history, operational runner, campaign ledger, registry, process receipts, raw logs, data archives, model weights, personal paths, contact information, credentials or private configuration.
3. Establish source rights for every addition. Record original or upstream provenance, exact source and public hashes, and every transformation. Preserve applicable license texts and notices. No blanket license for original HYDRA code may be added without the owner's explicit selection. Unresolved redistribution rights block that file, not unrelated safe work.
4. Make claims reviewable. Update status and validation documentation with scope, dates, failures, exclusions and unresolved prerequisites. A scientific result requires authenticated source/data lineage, declared splits and availability, qualified native/state/units/conservation checks where relevant, fair fixed-support baselines and complete result evidence. Generated examples must remain clearly synthetic. Research-exposed data cannot become a fresh holdout by renaming it.
5. Run focused checks in the isolated publication checkout. Prefer the tiny public demo and relevant tests. Model training, archive regeneration or heavy validation is outside a publication-only update. If separately authorized substantial work is needed, the coordinator must use its existing shared-host lease protocol before dispatch; do not invent a parallel registry or bypass a held lease.
6. Freeze the exact proposed commit/tree. Audit all staged paths and bytes plus the full history to be pushed, including commit identities/messages, ignored files accidentally staged, binary artifacts and links. Use pattern scans plus human-readable inspection; never open credential files to perform the audit. Obtain an independent reviewer for each publication batch, especially source additions, scientific claims and boundary changes. Review must identify the tree/commit and any blockers. Changed bytes after review require review of the new tree.
7. Publish through already authorized access only after that review passes. Use ordinary fast-forward pushes; preserve public history and prior links. Never force-push, change private repository visibility, grant account access, manipulate credentials or change security settings as part of this contract. A concurrent remote update requires fetching and reviewing the combined result before pushing.
8. Verify the public remote's visibility and exact commit, an anonymous fetch and browser rendering of the README and important links. Retain the reviewed manifest, validation evidence, independent verdict, resulting commit and verification record privately. Give downstream resume/website owners the verified URL. They own edits to those separate surfaces.

If evidence or safe access is unavailable, keep the prepared update local and report the concrete blocker. Preserve failed checks and older scientific history. No automatic public claim promotion is permitted.
